# UI And Data Entry Issues - 07/06/2026

This report covers the reported Create Booking and Pricing Rules issues, plus similar UI and data-entry problems found in nearby form-heavy admin screens.

## User-Reported Issues

### 1. Create Booking form is not cleared after successful submit

- **Severity:** High
- **Area:** Create Booking
- **Evidence:** `app/(tabs)/create-booking.tsx` has a complete reset path in `cancelBooking()` at lines 70-84, but successful `submit()` only shows a success alert and calls `router.replace("/(tabs)")` at line 144.
- **User impact:** After using `Create Booking` or `Create as Accepted`, the previous customer name, NIC, WhatsApp, email, selected track, date, people count, selected slots, remarks, payment method, and proof name can still be shown when the admin returns to the create screen. This makes the next booking easy to create with wrong details.
- **Recommended fix:** Reuse the same reset behavior after a successful booking save before navigating away, or reset the form when the screen regains focus after a successful create. Both `Create Booking` and `Create as Accepted` should clear the same fields.

### 2. Pricing rule edit modal has fragile touch behavior

- **Severity:** High
- **Area:** Pricing Rules / Edit Rule
- **Evidence:** `app/(tabs)/pricing.tsx` opens a parent `Modal` for add/edit rule at lines 235-273. Inside that modal, `SelectField` and `DatePickerField` controls open their own transparent modals. The parent modal also has an absolute backdrop `Pressable` at line 237.
- **User impact:** When editing a pricing rule, touching fields such as start time, end time, day type, effective dates, active state, or price can feel like the screen keeps navigating or jumping back to the wrong place. This is especially hard on mobile because nested transparent modals and backdrops can compete for touch handling.
- **Recommended fix:** Avoid nested transparent modals inside the Edit Rule modal. Use one modal layer with inline controls, or refactor the edit form into its own screen/bottom sheet where select/date controls do not fight the parent backdrop.

### 3. Pricing Rules can be edited but not marked as deleted

- **Severity:** High
- **Area:** Pricing Rules
- **Evidence:** `app/(tabs)/pricing.tsx` currently supports only `active` and `inactive` UI states, and each rule card only renders `Edit Rule` at line 230. `lib/pricingService.ts` has create/update/list functions, but no status update path for marking a price rule as deleted.
- **User impact:** Admins can correct or deactivate a rule, but they cannot mark accidental, duplicate, expired, or wrong pricing rules as deleted while keeping the DB record for history.
- **Recommended fix:** Add a delete action to each rule card with a confirmation dialog. Do not hard-delete the DB record. Update the existing price rule row by ID and set its status to `delete`, alongside the existing `active` and `inactive` states. Deleted rules should be hidden from normal active pricing selection and shown only where historical/audit visibility is needed.

## Additional Data Entry / Usability Issues

### 4. Default price changes are local-only

- **Severity:** Medium
- **Area:** Pricing / Default Price
- **Evidence:** `lib/pricingService.ts` stores `defaultSlotPrice` as a module-level variable and `updateDefaultSlotPrice()` only updates that in-memory value. There is no Supabase write for the default price.
- **User impact:** The default price can reset after app reload, app restart, or use from another device. Admins may believe they saved a real pricing setting when it was only changed locally.
- **Recommended fix:** Persist the default price in Supabase, preferably in an app settings table. Until persistence exists, mark the control as temporary or avoid presenting it as a saved business setting.

### 5. Block Slots form keeps old selections after save

- **Severity:** Medium
- **Area:** Block Slots
- **Evidence:** `app/(tabs)/block-slots.tsx` creates blocked slots, shows a saved alert, and refreshes the existing slots list at lines 61-74. It does not reset the date, start time, end time, reason, or track after save.
- **User impact:** Admins may accidentally submit the same blocked range again, especially because the selected values remain active after the save message.
- **Recommended fix:** After a successful save, either reset the form to safe defaults or clearly show that the same details are retained for another action. Add duplicate protection if the same track/date/time range is already blocked.

### 6. Settings controls look editable but are not all persisted

- **Severity:** Medium
- **Area:** Settings
- **Evidence:** In `app/(tabs)/settings.tsx`, notification toggles are local `useState` values at lines 18-24. `Max Slots Per Booking` is also local state at line 31 and only changes through the local stepper at line 105.
- **User impact:** Users can change settings that look saved, but those values can reset later. This reduces trust in settings and can cause admins to assume booking limits or notification preferences are active when they are not.
- **Recommended fix:** Persist these settings to Supabase or disable/label them until backend support exists. Saved settings should survive app reloads and be shared across admin sessions where appropriate.

## Test Plan For Future Fixes

- Create a booking with `Create Booking`; verify all fields clear after success.
- Create a booking with `Create as Accepted`; verify all fields clear after success.
- Reopen Create Booking after navigating away and back; verify no previous booking details remain.
- Edit one pricing rule field at a time: price, start time, end time, day type, effective from, effective to, and active status.
- Delete a pricing rule; confirm the same DB record remains, its status changes to `delete`, it no longer appears as an active pricing rule, and it no longer affects future pricing.
- Reload the app after changing default price and Settings values; confirm persisted values remain, or unavailable controls are not presented as saved.
- Save blocked slots twice with the same values; confirm the UI prevents duplicate entry or makes retained values obvious.

## Notes

- Existing bookings must continue to keep their original `booking_slots.price_at_booking` values. Pricing fixes should affect future pricing behavior only and must not rewrite old booking prices.
- Price rule delete must be a status change on the existing DB row, not a hard delete. Valid rule states should be `active`, `inactive`, and `delete`.
- This report is limited to UI and data-entry issues. It does not implement code fixes.
