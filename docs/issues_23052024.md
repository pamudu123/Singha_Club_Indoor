# Mobile App Audit Report

## 1. Executive Summary

This audit report delivers a rigorous technical evaluation of the Singha Club Indoor cricket booking system's mobile application. The target is an Expo Router React Native app integrated with Supabase JS v2 client-side libraries. 

The audit identified several **Critical** security vulnerabilities, **High** transactional reliability risks, and **Medium** layout and localization issues that must be addressed before the app is fit for production release. 

Key themes uncovered during the audit include:
- **Severe Security Vulnerabilities:** Bypassing authentication entirely using client-side admin fallbacks and attempting to use the highly sensitive database service role key (`SUPABASE_SERVICE_ROLE_KEY`) on the client.
- **Data Integrity and Transactional Fragility:** Performing multi-table inserts sequentially over a high-latency mobile connection without server-side transactions or RPC wrappers, which exposes the system to partial writes and orphaned records.
- **Incomplete Features and Client-Side Bottlenecks:** Hard-coded dashboards and reporting metrics, client-side filtering of unpaginated records, and non-functional document picker storage integration for payment receipts.
- **Aesthetic and UX Deficiencies:** Extreme layout risks on small device viewports, missing keyboard avoidance wrappers, and possible encoding corruptions on Sinhala localization dictionaries.

## 2. Supabase Credentials & Configuration Security

The client application includes patterns attempting to support and utilize the administrative service role key client-side. This constitutes a catastrophic security threat.

### Issue: Exposed Supabase Service Role Key and Server-Bypass Patterns
- **File:** [lib/supabase.ts:12](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/lib/supabase.ts#L12), [lib/supabase.ts:27-44](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/lib/supabase.ts#L27-44)
- **Severity:** `Critical`
- **Problem:** The client-side initialization script reads `SUPABASE_SERVICE_ROLE_KEY` directly from environment variables to construct a privileged client wrapper (`supabaseAdmin`). It also exposes `getWritableSupabase()` which falls back to this admin client if configured.
- **Why it matters:** The `service_role` key bypasses all Row Level Security (RLS) policies completely. Storing or referencing this key in a compiled mobile application bundle makes it trivially extractable via reverse-engineering or network traffic inspections, giving attackers absolute read and write access to the entire database.
- **Suggested fix:** 
  1. Remove all references to `SUPABASE_SERVICE_ROLE_KEY` and `supabaseAdmin` from the mobile client codebase.
  2. Implement secure server-side logic (e.g., Supabase Edge Functions or a proxy API) for administrative operations that cannot be handled via standard RLS policies.
  3. Ensure the mobile app *only* initializes the standard `supabase` client with the public `EXPO_PUBLIC_SUPABASE_ANON_KEY` as documented in [docs/mobile_app/db_connect.md:783-799](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/docs/mobile_app/db_connect.md#L783-799).

## 3. Authentication & Session Security

The current authentication mechanisms rely heavily on memory-only client variables, local bypass arrays, and lack route protection.

### Issue 1: Passwordless Admin Login Bypass
- **File:** [lib/authService.ts:28-53](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/lib/authService.ts#L28-53)
- **Severity:** `Critical`
- **Problem:** The `login()` method utilizes a nominal search against the `admin_users` table but implements a silent fallback to a static local profile (`localAdminId`) with no password verification or cryptographic handshakes.
- **Why it matters:** Anyone entering any arbitrary text in the login field can gain full administrative access. The fallback completely nullifies database-side security and allows unauthorized users to access tabs and make state changes.
- **Suggested fix:** Re-engineer the login process to use standard Supabase Auth methods (`supabase.auth.signInWithPassword()`) as outlined in the specifications, ensuring all users have verified credentials.

### Issue 2: Memory-Only Session State Persistence
- **File:** [hooks/useAuth.tsx:11-14](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/hooks/useAuth.tsx#L11-14)
- **Severity:** `Critical`
- **Problem:** The active session user profile (`admin`) is stored exclusively in a standard React `useState` memory hook inside `AuthProvider`. No local storage caching or active session restore routines exist.
- **Why it matters:** If the application is refreshed, background-suspended, or closed and reopened, the user session instantly vanishes, forcing the user to log back in repeatedly.
- **Suggested fix:** Query `supabase.auth.getSession()` on mount and register `supabase.auth.onAuthStateChange()` to automatically persist and restore the administrative profile from secure storage (e.g., using `expo-secure-store` or standard `AsyncStorage`).

### Issue 3: Unprotected Navigation Routes
- **File:** [app/index.tsx:4-6](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/app/index.tsx#L4-6), [app/_layout.tsx:15-20](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/app/_layout.tsx#L15-20), [app/(tabs)/_layout.tsx:10-36](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/app/%28tabs%29/_layout.tsx#L10-36)
- **Severity:** `Critical`
- **Problem:** Although the root index file redirects unauthenticated requests to login, the actual tab screens, layouts, and dynamic dynamic route bindings (such as `booking/[id]`) do not perform any authentication state validations on render.
- **Why it matters:** A user can bypass the login screen entirely by deep-linking directly into secondary paths like `/(tabs)/requests` or `/booking/id` using basic Expo Router navigation paths.
- **Suggested fix:** Implement route guard checks inside the `(tabs)/_layout.tsx` file and context provider to force a redirect to `/(auth)/login` if no authenticated admin session is active.

## 4. Row-Level Security (RLS) & Profile Model Alignment

The database profile schema conflicts directly with modern RLS patterns and standard Supabase Authentication concepts.

### Issue: Unlinked Admin User Profiles and RLS Incompatibility
- **File:** [lib/authService.ts:71-80](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/lib/authService.ts#L71-80) compared with [docs/mobile_app/db_connect.md:64-78](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/docs/mobile_app/db_connect.md#L64-78)
- **Severity:** `Critical`
- **Problem:** During the signup process, the application inserts an administrative record into the `admin_users` table with a custom, locally-generated UUID (`createAdminId()`) instead of linking it directly to a native Supabase Auth user ID.
- **Why it matters:** Because `admin_users.id` is not mapped to `auth.users.id`, Supabase's PostgreSQL database cannot recognize the active profile session. Consequently, RLS policies relying on `auth.uid()` comparisons will fail, rendering secure user-centric writes completely impossible.
- **Suggested fix:** 
  1. Use `supabase.auth.signUp()` to register users.
  2. Capture the returned user UUID from the auth session.
  3. Insert the profile record into `admin_users` using that exact returned UUID as the primary key.

## 5. Transactional Integrity & Booking Atomicity

Booking registration is highly fragmented, presenting severe risks of transaction failures and half-formed data models.

### Issue: Non-Atomic Multi-Step Sequential Inserts
- **File:** [lib/bookingService.ts:136-190](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/lib/bookingService.ts#L136-190)
- **Severity:** `Critical`
- **Problem:** The `createBooking()` flow executes six separate, sequential asynchronous queries to insert data into `customers`, `bookings`, `booking_slots`, `booking_payments`, `booking_status_history`, and `admin_activity_logs`.
- **Why it matters:** If the mobile client experiences a network failure, timeout, or validation error mid-process (e.g. after inserting the booking row but before reserving the slots), the database is left in a corrupted state. The customer may be charged, or a booking reference created, without reserving the actual court slot.
- **Suggested fix:** Consolidate these multi-table operations into a database-level transaction or a secure PostgreSQL RPC function. This ensures that either all rows are committed successfully or the entire operation rolls back safely (All-or-Nothing).

## 6. Storage Integration & Payment Verification

The workflow for uploading receipt files to verify offline transactions is incomplete.

### Issue: Incomplete Payment Proof Storage Flow
- **File:** [app/(tabs)/create-booking.tsx:80-84](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/app/%28tabs%29/create-booking.tsx#L80-84), [app/(tabs)/create-booking.tsx:103-114](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/app/%28tabs%29/create-booking.tsx#L103-114) compared with [docs/mobile_app/db_connect.md:398-428](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/docs/mobile_app/db_connect.md#L398-428)
- **Severity:** `High`
- **Problem:** When an administrator picks a file using `pickProof()`, the app only saves the local string file name into the database field (`payment_proof_path`) without actually uploading the file payload to a storage bucket.
- **Why it matters:** The administrative dashboard will display file names but will be unable to locate or render the receipt images. Financial audits will fail since the actual physical proofs are never saved on the server.
- **Suggested fix:** Implement standard Supabase Storage upload methods (`supabase.storage.from('payment-proofs').upload()`) inside the booking submission flow, and write the returned public URL or relative bucket path to the `booking_payments` row.

## 7. Race Conditions & Double-Booking Vulnerabilities

The slot reservation logic contains deep concurrency gaps that can lead to simultaneous court usage conflicts.

### Issue: Lack of Pre-Flight Conflict Checks
- **File:** [lib/bookingService.ts:157-167](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/lib/bookingService.ts#L157-167)
- **Severity:** `High`
- **Problem:** The booking creation workflow inserts requested slots into `booking_slots` without executing a transaction-isolated query to verify that those specific slots are not already flagged as `active` or listed in the `blocked_slots` database table.
- **Why it matters:** Two separate administrators (or a customer and an administrator) can book the exact same track at the same time, leading to scheduling conflicts and lost revenue.
- **Suggested fix:** Introduce an explicit pre-flight check inside an RPC transaction to ensure the requested slot array is entirely free before allowing the write transaction to finalize.

## 8. Data Hydration & Dashboard Reporting

Multiple key UI surfaces rely on static arrays, mock datasets, and inefficient querying habits that will bottleneck mobile performance.

### Issue 1: Hard-Coded Statistics & Chart Elements on Reports Screen
- **File:** [app/(tabs)/reports.tsx:12-28](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/app/%28tabs%29/reports.tsx#L12-28), [app/(tabs)/reports.tsx:54-60](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/app/%28tabs%29/reports.tsx#L54-60)
- **Severity:** `High`
- **Problem:** The reports dashboard is completely non-functional as it is backed entirely by static arrays (`barsDay`, `barsNight`, `timeBars`) and hard-coded values ("LKR 32,450", "18", "72%", "5").
- **Why it matters:** The admin dashboard displays fake statistics and completely fails to represent real-time booking trends, revenue gains, or slot occupancy rates.
- **Suggested fix:** Implement dynamic aggregation queries against `bookings`, `booking_slots`, and `booking_payments` grouping results by date range.

### Issue 2: Massive Unpaginated Fetching & Client-Side Filtering
- **File:** [lib/bookingService.ts:46-53](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/lib/bookingService.ts#L46-53), [app/(tabs)/requests.tsx:40-65](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/app/%28tabs%29/requests.tsx#L40-65)
- **Severity:** `High`
- **Problem:** The `listBookings()` method retrieves all records in descending order. The `RequestsScreen` then processes filtering (such as status, date, and track) entirely client-side using `useMemo`.
- **Why it matters:** As the club accumulates bookings over weeks and months, the app will download thousands of records, causing major cellular data consumption, layout freezes, and eventual out-of-memory crashes on mobile devices.
- **Suggested fix:** Rephrase database requests to utilize server-side filters (`.eq()`, `.gte()`, `.lte()`) and introduce pagination controls via limit and offset parameters.

### Issue 3: Inefficient Focus Fetching (Duplicate Network Calls)
- **File:** [app/(tabs)/requests.tsx:32-38](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/app/%28tabs%29/requests.tsx#L32-38)
- **Severity:** `Medium`
- **Problem:** The screen calls `refresh()` inside `useFocusEffect` which runs every time the screen is focused. However, the `useAsyncData` hook also executes the query immediately upon initial component mount.
- **Why it matters:** This triggers redundant back-to-back database calls when the page initially loads, increasing API costs and network latency.
- **Suggested fix:** Skip the initial auto-run in `useAsyncData` if the page relies entirely on `useFocusEffect` to handle mounting data retrieval.

## 9. Layout Usability & Small-Screen Responsiveness

The UI components lack responsiveness protections, threatening usability on smaller device displays.

### Issue 1: Lack of Keyboard-Avoiding Wrapper Constraints
- **File:** [components/ui/Screen.tsx:11-24](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/components/ui/Screen.tsx#L11-24)
- **Severity:** `Medium`
- **Problem:** The base layout container lacks an active `KeyboardAvoidingView` or layout-offset wrapper.
- **Why it matters:** On small Android or iOS devices, opening the keyboard on input-heavy screens (like Signup or Create Booking) completely covers the active input fields and primary submit buttons.
- **Suggested fix:** Wrap the core content structure in React Native's `KeyboardAvoidingView` with correct behavior configurations matching OS types (e.g. `behavior={Platform.OS === "ios" ? "padding" : "height"}`).

### Issue 2: Small-Screen Overflow & Clipping Risk
- **File:** [app/(tabs)/schedule.tsx:45-61](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/app/%28tabs%29/schedule.tsx#L45-61), [app/(tabs)/reports.tsx:102-123](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/app/%28tabs%29/reports.tsx#L102-123), [app/(tabs)/settings.tsx:157-199](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/app/%28tabs%29/settings.tsx#L157-199), [components/ui/SelectField.tsx:44-58](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/components/ui/SelectField.tsx#L44-58)
- **Severity:** `Medium`
- **Problem:** Layouts use strict horizontal alignments (like side-by-side card items or 7-day strips) without flex wrapping or scroll protection.
- **Why it matters:** On narrower screens (e.g. iPhone SE), horizontal items will overflow, clip edges, overlap text, or compress interactive elements (such as select items or increment buttons) into unusable spaces.
- **Suggested fix:** Replace restrictive layouts with adaptive column flex systems or wrap horizontal strips in side-scrolling views (`ScrollView horizontal`).

## 10. Localization, Assets & Sinhala Text Encoding

Direct embedding of localized languages creates risks of compilation glitches and character corruptions.

### Issue: Raw Character Encoding Risk on Sinhala Dictionaries
- **File:** [hooks/useLanguage.tsx:40-70](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/hooks/useLanguage.tsx#L40-70), [app/(tabs)/settings.tsx:74-76](file:///c:/Users/PK/Desktop/projects/Singha_Club_Indoor/app/%28tabs%29/settings.tsx#L74-76)
- **Severity:** `Medium`
- **Problem:** Raw, unescaped Sinhala Unicode strings are written directly into standard TypeScript source files.
- **Why it matters:** If the compiler, bundler, or local text editor is not configured to save and build files in strict UTF-8 formatting, characters can get corrupted into garbage symbols. String comparisons (such as `value === "සිංහල"`) will fail silently.
- **Suggested fix:** Extract the dictionary files into localized JSON files (e.g., `si.json`) loaded explicitly using standard Unicode escape characters or set up build-level validation gates to enforce UTF-8 source file encoding.


### 12.2 Manual Testing Scenarios

Use the following manual validation matrix to verify all subsequent fixes:

#### Scenario A: Authentication
- **Test A.1:** Attempt login with an invalid or unregistered user. System must reject access (no bypass fallback allowed).
- **Test A.2:** Log in, close the app completely, and reopen. Verify the session is restored successfully without requesting credentials.

#### Scenario B: Booking Concurrency
- **Test B.1:** Attempt to submit a booking for a slot that has already been booked or blocked. Verify that the app rejects the action and reports a booking conflict error.
- **Test B.2:** Disconnect network connectivity midway through a booking insertion process. Confirm that no partial customer or booking rows are saved (atomic rollback validation).

#### Scenario C: Payment Proof Storage
- **Test C.1:** Create a booking with a payment receipt document. Verify the file uploads to the `payment-proofs` bucket and that the saved relative path loads correctly inside the administration dashboard.

#### Scenario D: Layout & Usability
- **Test D.1:** Open the booking form on a small screen device (e.g. iPhone SE emulator) with the soft keyboard active. Verify all fields scroll smoothly into view and are not obscured by the keyboard.
